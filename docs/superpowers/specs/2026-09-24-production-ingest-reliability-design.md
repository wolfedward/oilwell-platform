# WP-03 异常报文持久隔离与应用入库回执设计

## 1. 用户目标与成功标准

把采集链路从“消息交给 Broker”推进到“中心已可靠保存、网关知道保存结果、异常可追查”，继续沿用 Modbus TCP/RTU 只读采集与 MQTT 上行。保持现有遥测格式，不重新设计整套设备协议。

用户已认可四项范围：异常报文持久隔离、同事务待发回执、网关校验应用回执、受权限控制的异常处置页面。本稿将故障、兼容性和验收规则具体化，供书面确认。

成功必须可核对：

- 坏报文保存后不再靠持续断开 MQTT 连接处理；其后的合法报文能继续入库。
- 数据库事务未成功提交时，不发送中心接收确认，也不产生“已入库”应用回执。
- 数据已提交但网络中断、进程重启或确认丢失时，能够恢复发送；重复报文不重复插入测点。
- 网关只在收到身份、报文编号、原始字节摘要均匹配的合格回执后，结束该报文的正常重发。
- “已隔离”“仅 Broker 确认”“中心已入库”分别展示，不把技术接收成功当业务数据合格。
- 保留合法但未登记、质量不佳或点表不匹配的原始数据；不自动登记设备、不自动取得算法或控制资格。
- 冻结演示版、既有业务库和运行服务不因本设计或隔离环境研发被改动。

## 2. 现状证据与方案选择

已核对的实现：

| 位置 | 当前行为 | 本轮缺口 |
| --- | --- | --- |
| `backend/center/ingest.py` | 严格校验 v1 主题、原文与身份；计算原始字节 SHA-256 | 永久输入错误与部分服务器错误共用异常类型，不能简单全部隔离 |
| `backend/center/postgres.py` | 消息、测点同事务；全局 message_id 去重；同编号不同摘要报冲突 | JSONB 不是逐字节原文；没有持久隔离或待发回执 |
| `backend/center/mqtt_consumer.py` | 入库后手动 PUBACK；任意处理异常会断开重连 | 永久错误报文也反复重投，可能阻塞后续接收 |
| `backend/gateway/mqtt_uplink.py` | 收到 Broker PUBACK 后将本地记录标为 acked | 没有订阅中心应用回执；不能据此证明中心入库 |
| `backend/gateway/spool.py` | SQLite 持久队列、租约、重试；达到次数上限转 dead，原文仍保留 | 没有应用确认、隔离结果及新旧确认模式区分 |
| `backend/registry/resolution.py` | 合法原始测点只读关联登记、历史井号、质量原因 | 必须维持此观察边界，不能改成未知设备数据一律丢弃 |

采用已认可的完整闭环：中心持久隔离 + 同事务回执记录 + 独立发送器 + 网关应用确认。仅增加隔离无法解决端到端确认；整体重做协议会扩大本轮风险。

技术依据：MQTT QoS 针对一次发送方与接收方之间的交付，Broker 的 PUBACK 不是数据库提交证明；Paho 的手动确认适合放在应用持久化之后。以下状态机是项目设计，不是 MQTT 自带的数据库事务能力。[MQTT 5.0 §4.3](https://docs.oasis-open.org/mqtt/mqtt/v5.0/os/mqtt-v5.0-os.html)、[Paho 客户端确认接口](https://eclipse.dev/paho/files/paho.mqtt.python/html/client.html)。

## 3. 输入分类：什么保存、什么隔离、什么重试

| 情况 | 持久化结果 | 中心对入站 QoS 1 的处理 | 应用回执 |
| --- | --- | --- | --- |
| 合法新报文 | 原消息、全部测点、精确原文；适用时创建回执 | 提交成功后 PUBACK | stored |
| 相同 message_id、身份及字节摘要重投 | 不重复写测点；补齐原文证据或重新请求已有回执发送 | 上述事务提交后 PUBACK | 同一个 stored 回执 |
| 合法但未登记、未绑定、停用、质量 bad/uncertain、工程范围或期望点表不匹配 | 仍按合法遥测保存；来源核查保留相应原因 | 提交后 PUBACK | stored，仅表示原始数据已保存 |
| 永久输入错误：非法主题、UTF-8/JSON/契约不合格、主题身份不符、编号内容冲突等 | 隔离精确原文和原因，不插入本次测点 | 隔离及适用回执同事务提交后 PUBACK | 能安全关联时 quarantined，否则不发应用回执 |
| 数据库不可用、超时、容量不足、提交结果不确定 | 不把未证实的保存当成功 | 不 PUBACK；恢复连接后重试 | 不发送未提交结果 |
| 服务器时钟配置错误、程序错误、内部不变量破坏 | 记录不含敏感原文的系统告警 | 不 PUBACK；进入系统故障处理 | 不伪造成输入拒绝 |

实现必须有明确的永久输入错误代码；禁止 `except Exception -> quarantine`。现有“中心时钟必须带时区”错误须归入系统故障，即使其当前类名含 Validation。

对同一原文按稳定顺序确定首要原因，保存验证器版本；原因只用有限枚举与受控说明，不持久暴露驱动堆栈、连接串或任意异常文本。重复键、非法数字词法等 WP-01 校验不能放宽。

首版拒绝代码限定为 `topic_invalid`、`payload_too_large`、`utf8_invalid`、`json_invalid`、`json_duplicate_key`、`contract_invalid`、`identity_mismatch`、`idempotency_conflict`、`qos_not_supported`、`retained_publish`。超过隔离硬上限属于无法安全处理的容量错误，不声称已经隔离。首次判定按大小、主题、传输约束、编码/JSON、契约、身份、编号冲突依次检查；已有持久结果按第 4 节复用，不重新改判。

QoS、retain、dup 记录为中心观察到的传输元数据，不冒充 Broker 已认证的发布者身份。接收订阅使用 Retain As Published，以便识别不符合接口的保留发布。收到 QoS 0 可尝试留存并告警，但协议没有可延后的 PUBACK，不把此情况计入可靠交付保证；订阅降级后的 QoS 也不能证明发送端原始 QoS。

## 4. 中心存储边界与事务

在现有遥测同一 PostgreSQL 数据库新增独立命名空间 `ingest_reliability`，不引入跨库事务。保留 public 中的消息、分区测点及全局 message_id 含义。

逻辑记录划分如下；迁移记录、约束和精确授权随实现计划细化，不把几种不同确认混在一列：

| 记录 | 不可变事实 | 允许变化的部分 |
| --- | --- | --- |
| 接收事实与精确原文 | 事实编号、精确主题、原始 BYTEA、SHA-256、字节数、首次元数据、解析版本及 stored/quarantined 结果；stored 关联原消息，quarantined 保存拒绝代码 | 无；两类结果共用唯一性约束，原有 JSONB 查询接口保留 |
| 隔离案件 | 关联隔离编号 | 首末见时间、重复计数、open/acknowledged/closed 状态、处置版本；事实与人工状态分开 |
| 应用回执 | receipt_id、目标主题、关联报文与摘要、stored/quarantined 结果、完整回执字节 | 无；一个回执仅关联接受事实或隔离事实之一 |
| 回执投递记录 | receipt_id 关联 | 请求/已发代次、租约令牌、重试时间、次数、最近安全错误、Broker 确认时间 |
| 处置审计与操作幂等记录 | 操作者、操作、原因、前后状态、请求摘要、幂等键、时间与返回结果 | 只追加，不改写历史 |
| 发送器健康记录 | 实例标识 | 有期限的心跳、最近成功/失败、受控错误码；不是设备在线证据 |

关键事务规则：

1. 接受路径一次提交消息、所有测点、精确原文和适用回执。任何一步失败整笔回滚；“回执入表失败但数据照常确认”不允许。
2. 隔离路径一次提交原文、案件及适用回执。隔离保存失败时不确认接收；合法历史消息不受编号冲突报文影响。
3. 编号冲突的判定在并发安全的数据库路径完成。新报文内容不覆盖既有消息，不通过忽略数据库约束错误掩盖内部故障。
4. 接收事实按精确主题与原文字节摘要唯一，并核对字节一致性；首次成功提交的结果固定。不能因验证器升级、retain/QoS 变化或人工关单，将同一事实先判 quarantined 再判 stored，或相反。已有旧版接受消息优先保留其接受事实；后续传输异常另记安全事件，不生成与旧事实矛盾的回执。此前已隔离的输入不自动重新解释为测点，修正设备后以新编号采集，历史纠错另行设计。
5. 同一隔离事实重投复用隔离编号，只更新有界统计；再次出现已关闭案件时自动重新打开，并追加系统事件。计数达到数据库上限后饱和并标明，不因统计溢出丢弃原文。
6. 同一个合格回执因入站重投或授权人工操作重新请求发送，不改变回执结果或生成无限重复正文。请求代次受并发保护；已在等待的请求可合并。
7. 所有提交结果不确定的情况都允许原请求重试；不能靠内存中的“已处理”集合确认成功。

旧数据没有精确原文时明确显示“旧记录仅有 JSONB 与摘要”。只有收到与旧摘要完全匹配的重投，才能追加真实字节档案；不得把 JSONB 重新序列化成声称的原文。旧的 stored 事实可在验证重投后形成新回执，不编造历史发送时间。

## 5. 应用回执契约（待本设计和实现验证后冻结）

v1 遥测主题与 payload 不变。新增回执主题：`{prefix}/v2/{gateway_id}/{device_id}/ingest-ack`，QoS 1、retain=false。这是独立回执契约，不表示 v2 配置、波形或控制接口已经开放。

回执为严格 UTF-8 JSON 对象，上限 4 KiB；字段全为字符串，不接受数组或嵌套对象，拒绝重复/未知字段及错误类型，标识沿用 v1 校验，时间使用带微秒的 UTC。字段确定为：

| 字段 | 约束与含义 |
| --- | --- |
| schema | 固定 `OWP-INGEST-ACK/1.0` |
| receipt_id | 中心生成的 UUID，同一持久结果重发不变 |
| gateway_id、device_id、message_id | 必须与目标主题及本地待确认报文一致 |
| payload_sha256 | 原始上行字节的 64 位小写十六进制 SHA-256，不摘要归一化 JSON |
| status | 仅 stored 或 quarantined；不增加含义模糊的 success |
| reason_code | stored 时固定 accepted；quarantined 时为公开的有限拒绝代码 |
| recorded_at | 该结果首次在事务内记录的 UTC 时间；不是精确 WAL 提交时刻，只有事务提交后才能发布 |

重复入站本身不是新的持久结果，因此仍返回原 stored/quarantined 回执，中心另计重复接收次数。不用可变的 duplicate 标志改写已持久化回执。

安全关联规则：

- 回复地址只由经过校验的入站主题派生，不使用报文提供的任意 Response Topic、URL 或收件人。
- 合法输入可以直接关联。输入不满足完整遥测契约时，仅当整个 JSON 仍能经有界、无重复键的严格解析，schema 与三个标识有效、主题身份一致，才允许为该 message_id 生成 quarantined 回执；不扫描坏文本猜编号。
- 无法可靠识别编号、主题非法或主题与包内身份冲突时，只持久隔离后完成 MQTT 接收；不向任意身份发送猜测的应用回执。对应网关会保持未确认并告警，需查隔离记录处理，不能宣称所有畸形输入都能自动闭环。
- 身份、编号相同但内容冲突的拒绝回执只带本次原文摘要，不泄露既有报文内容或其他设备身份。
- SHA-256 是内容匹配凭据，不是身份签名。安全前提是可信 Broker、TLS、独立身份及逐主题 ACL；不声称能够抵御已被攻陷的 Broker。

首版用中心配置中的明确网关允许列表启用应用回执，默认列表为空；不从发现消息或设备登记状态自动启用。隔离功能与此列表无关。属于列表中网关的终端才生成适用回执，避免未升级网关长期积压无人订阅的回执。网关进入 application 模式前须完成中心允许列表和 ACL 的部署核验。已产生的待发回执不因后来从列表移除而删除；停止回执服务必须按协调回退处理。第 3 节回执列均以本节启用及安全关联规则为前提。

## 6. 回执发送与崩溃恢复

接收器只负责事务及入站确认，不在入站网络回调中等待回执发布。使用独立发送器进程和 MQTT 身份，从已提交的投递表领取任务。

- 短数据库事务领取有期限的租约，提交后才进行网络操作。可以用 `FOR UPDATE SKIP LOCKED` 领取待发记录；只用于工作队列，不用于普通业务查询的一致性判断。[PostgreSQL 锁定子句](https://www.postgresql.org/docs/18/sql-select.html#SQL-FOR-UPDATE-SHARE)。
- 每次领取获得独立令牌和请求代次。发布后回写须同时匹配令牌/代次；过期发送器不能覆盖新租约。领取期间新增发送请求不能被旧成功回写吞掉。
- 发送者收到成功的 Broker PUBACK 后，标记该代次“已交 Broker”；No matching subscribers 或失败原因不能标成功。网络超时、ACL 拒绝或数据库回写失败继续重试并告警。
- 重试采用有上限的指数退避及抖动；中心回执不因次数达到上限而自动删除或永久停止。发送后、状态写回前崩溃可能重复发布，网关必须幂等接收。
- 回执已交 Broker 但网关没有收到时，由网关以同一应用编号和精确正文重新发布遥测，中心请求补发原回执。不能依赖 Broker 永久保留会话或无容量限制。
- 本轮不增加“回执的回执”。因此中心界面最高只能显示“回执已交 Broker”；“网关本地已确认”只有网关本地持久记录能证明，不编造远端状态。

应用重试是新的 MQTT 发布，复用的是应用 message_id 和正文，不手工伪造 Packet Identifier 或 DUP。上述重试与去重提供至少一次传输下的幂等入库，不宣传端到端 exactly-once。[MQTT 5.0 §4.4、§4.10](https://docs.oasis-open.org/mqtt/mqtt/v5.0/os/mqtt-v5.0-os.html)。

## 7. 网关本地状态与升级兼容

确认模式显式配置为 broker 或 application，并在每条队列记录入队时固定。默认兼容旧配置为 broker，但日志和状态须明确“仅 Broker 确认，未启用中心入库确认”；生产新配置模板推荐 application，不能运行中静默降级。

application 模式的逻辑状态：

| 状态 | 含义与后续 |
| --- | --- |
| pending | 已在 SQLite 持久保存，等待发送 |
| inflight | 发送租约内，等待本次传输结果；不是中心成功 |
| awaiting_receipt | Broker 已确认，仍保留原文，等待应用回执 |
| stored | 匹配的 stored 回执已经与本地状态同事务保存，结束正常重发 |
| quarantined | 匹配的拒绝回执已保存；结束同一坏报文的正常重发，保留原文及原因待处理 |

恢复规则：

1. 独立、有界的网络工作单元先建立订阅并核对 SUBACK，再发送 application 记录。采集循环只写持久队列，不逐条等待中心回应；断网不能把每轮 Modbus 轮询阻塞在累计回执超时上。
2. Broker PUBACK 只推进到 awaiting_receipt。应用等待超时按退避重新发布原 message_id、原主题和原字节；长期断网仍可重试，不沿用 broker 模式“12 次后转 dead”的终止规则。
3. 校验回执主题、schema、编号、身份和 SHA-256 后，SQLite 事务同时存回执与最终状态。只有本地保存成功才对该 QoS 1 回执手动确认；本地失败不把内存匹配当成功。
4. 回执可能先于 PUBACK、租约到期后或进程重启后到达。只要匹配已有 application 记录，即可完成待处理状态；迟到的传输失败、旧租约或 PUBACK 不能把最终状态改回 pending。
5. 重复相同回执无副作用；未知编号、错误摘要、错误设备或保留回执不改变队列，回执订阅也须启用 Retain As Published。非法回执用本地有界持久事件按主题/摘要合并记录，记录成功后可以完成其协议确认；保存失败不确认。不能用它制造永久重连风暴。同一报文出现互相矛盾的持久结果时保留冲突事件并告警，不能静默改判。
6. 本地同编号再次入队必须比较精确主题和正文：完全相同为幂等，不同则拒绝并告警，不能继续使用 INSERT OR IGNORE 掩盖冲突。

应用模式下，超过重试次数仅触发告警，不清除记录；quarantined 也不是完成业务数据处理。首版不远程编辑/清除队列，不把修改后的报文冒充原消息，设备配置修正后的新采集使用新 message_id。

SQLite 结构采用显式、版本化、事务性迁移。迁移前停止该队列所有写进程并保存一致备份，包括 WAL 中数据；迁移复制/重建不得丢失原文字节和历史状态。旧记录一律标记 broker 模式，旧 acked 显示 legacy_broker_confirmed，旧 dead 继续保留；不自动重发旧成功记录，不将旧确认升级成应用确认。新模式只影响新入队记录。

禁止旧程序打开升级后的队列继续写入；升级/回退入口必须检查结构版本。回退不能直接恢复过时备份抹掉升级后新采集，须先停采集并保全新队列，再使用独立新路径恢复兼容服务。此限制应写进部署说明和失败演练。

## 8. 处置界面、接口与权限

接入现有平台的采集管理，新增“接收异常与回执”工作区；复用账号、导航和错误展示，不建立第二套用户系统。页面必须分开显示隔离案件、原始事实、回执发送状态及链路健康。

首版能力：

- 按网关/终端、message_id、时间、原因和处置状态分页查询；单条查看原文摘要、首末见、重复次数与审计历史。
- 正常列表不返回原文字节。单条原文访问使用额外权限，预览最多 4 KiB 并明确截断；按文本转义，不执行 HTML/SVG/脚本。授权下载提供精确字节、摘要、固定安全文件名及 attachment/nosniff 响应，不把二进制伪装成可执行网页。
- 支持案件确认、关闭、重新打开、补充说明，以及已有合法回执的人工“重新请求发送”。必须填写原因，携带预期版本和幂等键；状态变更、审计、幂等结果同事务。
- 关闭案件只表示人工处理状态，不删除隔离原文、不写入测点、不变更 quarantined 回执。首版不提供修改原文后自动重放或批量删除。
- 查询故障显示不可用，不显示假空数据。模块未配置时隐藏操作入口；有权限直接访问时明确提示未配置。

HTTP 使用独立 `/api/ingest-reliability` 域，写请求复用已验证的认证、Origin/CSRF 与请求限额模式；不挪用台账操作权限。重试必须重新鉴权，不因存在幂等回执绕过撤权。响应不确定时前端保存原请求/原幂等键，不能换键重复操作；切换设备或关闭窗口后旧响应不得覆盖新页面。

拟新增权限及默认岗位分配：

| 权限 | 能力 | 默认岗位 |
| --- | --- | --- |
| ingest.read | 案件、回执、健康摘要查询 | 系统管理员、生产工程师、算法工程师、设备运维、业务复核员 |
| ingest.raw.read | 单条原文预览/下载，访问记审计 | 系统管理员、算法工程师、设备运维 |
| ingest.manage | 案件处置与回执重新发送请求 | 系统管理员、设备运维 |
| audit.read 与 ingest.read | 查看本模块审计历史 | 沿用账号实际授权；系统管理员包含全部权限 |

原文读取/下载的审计必须成功记录“访问获准”后才返回内容；不能把审计记录误称为用户已下载完整文件。生产工程师和复核员可以查异常及处理结果，但默认不能改通信处置；后台按权限逐项判断，不用前端隐藏按钮替代鉴权。

## 9. 容量、安全与可观测性

v1 有效 payload 上限仍为 1 MiB。隔离单条原文上限设为 2 MiB，以保留一部分超出 v1 的错误输入；超过隔离能力时不以截断摘要代替原文并确认成功。提供显式 Broker 报文限额模板，完整 MQTT 包上限不得大于接收隔离硬上限；有效 v1 payload 的主题/头部/属性需留余量并用边界测试确认。

Broker 的 `max_packet_size` 限制整包，`message_size_limit` 限制 payload；二者拒绝路径不同，不能把协议确认一概算成成功。Broker 队列也可能达到容量上限，因此本设计仍需本地保留和应用重试。[Mosquitto 配置说明](https://mosquitto.org/man/mosquitto-conf-5.html)。本轮只修改候选模板与隔离环境，不直接修改现有 Broker。

运行限额必须可配置并有正数上界校验：本地记录数/字节预算、最低磁盘余量、中心原文总预算及隔离子预算、MQTT 处理中数量、数据库等待和发布超时。字节预算检查必须与写入并发安全地扣减/回滚，不能多进程各自先查后写突破额度；逻辑字节数不等于含索引/WAL 的实际磁盘用量，仍需独立空间告警。示例值仅作为测试起点，不能在无井数/采样率依据时宣称满足生产容量。

- 单条精确原文写入失败或中心容量保护触发，不 PUBACK。重复隔离优先复用原文，不能每次重投新增一份大对象。
- 网关空间不足时拒绝新的持久入队并触发明确采集缺口告警；不覆盖最早未确认数据，不自动删除 quarantined 或 legacy 记录。已发生的采样缺口不能显示成完整连续数据。
- 首版不自动清除原文、幂等事实或回执。本轮提供容量计算与备份检查说明，长期保留/归档策略在生产部署前必须核定；有限磁盘不是无限可靠缓存。
- 超时用于及时告警和重试，不能据此伪造对方成功；等待计时采用单调时钟，持久事件用 UTC，重启后的到期判断处理时钟回退并提示异常。
- 日志/页面提供：隔离数量及最近增长、最老未处置年龄、待发回执数和年龄、发送失败原因、发送器心跳。网关本地另外报告待应用确认数、最老等待时长、隔离/确认数及空间状态；中心不假装已收到这些尚未上行的本地指标。
- 告警阈值为运维参数，不是抽油机安全保护整定。缺配置、心跳过期或数据库不可用不得显示为绿色健康；读取健康接口也要鉴权。

MQTT ACL：网关只能写自身 v1 遥测、读自身 v2 回执；禁止其写任何回执主题或读取其他网关回执。中心接收身份保持只读遥测；独立回执发布身份只写回执域。TLS 验证不得为联调方便而在远程配置中禁用；本轮不开展凭据自动签发、轮换或设备控制。

## 10. 数据库权限、启用与回退

不在启动时建库、执行 DDL、授予权限或使用管理员账号补救。采用显式迁移版本与校验摘要；缺表、结构漂移或越权配置时清晰拒绝启用新能力。

设计中的数据库身份隔离：

- 迁移身份：拥有新命名空间及迁移/约束管理能力，仅离线部署使用。
- 新可靠接收身份：具备现有遥测必要插入/去重读取、新原文与结果插入，以及限定的接收统计/请求发送列更新；没有原文修改、删除、台账写入、建表权限。**不直接给现有入库账号提权**。
- 回执发送身份：只读回执正文及更新投递租约、进度、心跳；不能改回执内容、遥测、隔离原文或人工处置结论。
- 运维查询身份：仅查询受限元数据视图；没有通用原文字节读取权限。
- 运维服务身份：受限地读取单条原文、追加访问审计、执行处置事务及重新请求回执；没有遥测或原文修改/删除权限。

数据库级列授权、不可变约束及实际权限预检要一并测试。应用权限负责区分登录用户，数据库身份负责限制服务的最大权限；二者不能相互替代。保留 WP-02 台账角色独立性，不为新页面放宽其旧权限检查。

新能力由独立开关启用，旧配置继续按旧链路运行且明确标为 legacy。启用新可靠接收模式时必须完整通过结构、权限和连接预检，失败即退出该新接收实例，不能回退成“先确认后保存”。界面不可用不能拖垮已正确配置的中心接收。

候选发布顺序：隔离环境通过 → 明确部署授权 → 备份/迁移与新身份 → 新中心及发送器健康核验 → 逐网关配置回执允许列表、ACL 和 application 模式 → 观察积压。此顺序是设计约束，不是本轮执行部署的授权。

回退优先关闭新入口或界面、保留数据库增量和队列事实，不下发 DROP 或删除历史。网关仍为 application 时，中心退回旧接收器会造成等待与重发，应明确告警并安排协调回退，不能把现存 application 记录改为 Broker 确认来消除告警。

## 12. 验收矩阵

测试必须在隔离数据库、临时 Broker 与独立队列完成；数据库套件串行，避免互相清空测试状态。故障必须从真实边界注入，不以网页静态文案或 mock 成功代替全部证据。

| 场景 | 必须看到的结果 |
| --- | --- |
| 首次合法输入、相同输入并发/重投 | 一条消息与应有测点；精确原文一致；一份稳定结果，可补发回执 |
| 坏报文后紧接合法报文 | 坏原文可追查且无测点污染；持久隔离后连接继续服务合法报文 |
| 未注册、质量 bad、点表不匹配、台账不可用 | 合法原始数据仍入库；不自动登记、不获得算法/控制资格 |
| 同编号不同正文及并发冲突 | 原接受事实不变；冲突正文单独隔离；拒绝回执仅关联本次内容 |
| 同一原文在传输标志改变、关单或验证器更新后重投 | 复用持久结果，不产生相互矛盾的回执；新增异常单独记事件 |
| 原文/测点/隔离/回执任一步写入失败 | 整笔回滚或结果不确定后安全重试；中心不提前 PUBACK |
| 数据提交后入站 PUBACK 丢失 | 重投不重复测点；原回执可恢复发送 |
| 发布前崩溃、发布后状态回写前崩溃、双发送器租约交叠 | 恢复后可发；允许幂等重复；旧租约不能覆盖新状态/请求 |
| Broker 重启、回执无人订阅、ACL 拒绝、会话丢失 | 未证实结果不变成成功；待发和等待状态可见并能够恢复 |
| 应用回执先于 PUBACK、迟到、重复、网关重启 | 匹配记录只完成一次；旧回调不能逆转最终状态 |
| 错误摘要/身份/未知编号/保留或畸形回执 | 不完成其他报文；安全事件有界；不形成坏回执重连风暴 |
| 本地提交失败、满盘、空间阈值、时钟回退 | 不凭内存确认；有缺口/容量/时间告警；保留未确认原文 |
| 中心内部时钟/程序错误 | 不误隔离合法输入，不把系统故障归罪于设备 |
| 无法提取安全关联的畸形 JSON | 原文隔离后只做 MQTT 确认，无猜测式应用回执 |
| 限额边界与恶意原文 | 大小/深度/数量边界可控；无前端执行、日志秘密泄露或越权下载 |
| 新旧模式、旧队列迁移、失败回退 | 旧确认仍为旧语义；原文不丢；不把未确认记录强改成功 |
| 越权、撤权重试、重复/并发处置、审计失败 | 后台拒绝或幂等；预期版本有效；审计失败不留下未记录的状态变化 |
| 真实页面操作与前端竞争 | 能筛选、查详情、授权看原文、处置、重新请求回执；旧请求不覆盖新选择 |
| 全项目回归与保护核验 | 旧采集/台账/诊断流程不退化；冻结演示版及既有服务未被本轮研发改动 |

最终证据应分别列出单元测试、真实 PostgreSQL 事务/角色/并发、真实 Broker 链路、重启故障注入及真实浏览器结果，附版本、退出码和日志位置。不把历史 WP-02 的 634 项通过当成本工作包的测试结果。

## 13. 明确不做与后续门槛

本轮不实现：自动设备发现/激活、点表远程下发、隔离原文自动重放、远程启停、Modbus 写操作、同步波形、功图算法精度验证、实际节能验证、硬件安全保护、整个平台高可用部署及凭据生命周期自动化。

真实设备缺失不阻塞本工作包的软件闭环，但厂家联调、生产容量/保留期、非本机网络与 TLS 运维、备份恢复演练仍是投产条件，不能由“软件测试通过”替代。

本稿审阅通过后才形成实施计划，细化任务、预计周期、测试证据与执行方式；实施计划获得确认后开始产品改动。生产业务库迁移和运行服务切换继续另行取得明确授权，独立演示版长期保留。
